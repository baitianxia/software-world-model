# 架构文档

架构层描述顶层关系和选择；Contract 拥有精确跨模块语义；代码和测试拥有局部实现。

唯一的顶层架构基线是 [Software World Model 架构基线](architecture-baseline.md)。所有架构讨论、设计评审和架构变更必须先以该文档为准。

架构基线是完整架构设计，不是模块目录、摘要或实现状态说明。任何修正必须在保留原有章节、概念、约束、关系和架构图的前提下增量修改；只有已经通过架构决策明确废弃的条款才能删除或改写。审计收敛不得以压缩正文、迁移摘要或新增模块介绍替代原设计。

基线第 1 至 13 章直接承载当前架构语义；文末第 14 节仅是非规范审计记录，不覆盖正文、不产生第二套适用规则。开发和评审不需要在第 14 节与正文之间做优先级选择。

为避免自动阅读器把附录、兼容投影或审计记录误当成第二个架构入口，按下表解释文档权威：

| 文档范围 | 语义所有者 | 是否可以新增或收窄顶层架构语义 |
|---|---|---|
| `architecture-baseline.md` 第 1—13 章 | `SYS-ARCH-BASELINE` | 可以，且必须通过架构变更流程 |
| `architecture-baseline.md` 第 14 节 | 无（审计记录） | 不可以 |
| 本目录其他架构文件 | `SYS-ARCH-BASELINE` | 不可以，只能解释或细化 |
| `decisions/ADR-*.md` | `SYS-ARCH-BASELINE` | 不可以，只记录决策理由和迁移关系 |

文件的 `authority: normative` 只表示内容属于当前文档集合并受文档治理；它不改变上表的语义所有权。自动化开发阅读顺序应先读取基线第 1—13 章，再按需要读取附录或 ADR；若发现冲突，直接回到基线，不自行合并两种解释。

本架构基线描述长期目标和稳定边界，不是某一期的实现清单。阶段目标可以从基线中选择可验证的能力切片；实现 Agent 可以在该切片内自行决定 API 字段、类、表、Prompt、Tool Schema、算法和物理存储，只要不违反基线不变量、Owner、依赖、权威和生命周期约束。只有当实现选择改变跨模块语义时才需要补充或修正 Contract；改变顶层职责、权威或不变量时才进入架构变更流程。

## 架构变更唯一流程

架构变更必须按以下顺序进行，不能在产品实现提交中隐式完成：

1. 在项目文档中登记变更原因、受影响的基线章节、替代方案和最早可证伪证据。
2. 形成并接受对应 ADR；ADR 只记录决策原因和迁移关系，不单独改变当前架构语义。
3. 在同一架构变更中增量修改本基线，明确标记新增、修改和废弃条款；不得用摘要、模块介绍或新文件替代原章节。
4. 同步修正受影响的架构附录和 Contract，并清理被替代条款，不能保留两个互相冲突的 `current` 解释。
5. 仅在架构语义确实改变时，更新 `docs/project/current.md`、活动 Manifest 的 System 引用和生成索引，运行文档检查；这些引用同步不改变 Iteration 的授权、暂停或执行状态。

普通产品 action 不得通过修改 `docs/system/architecture/**` 或 `docs/system/contracts/**` 改变系统语义。需要修改这些路径中的语义时，必须使用独立的架构变更动作，并在交接前提供基线语义差分；仅通过测试、收据或目录检查不能证明架构变更正确。纯索引、链接、来源标注和历史状态整理不构成架构变更，但不得借整理之名删除或收窄架构内容。

架构基线的章节、关键概念、组件关系和架构图属于受保护内容。没有明确废弃记录时，删除其中任一项都视为架构变更，而不是文档重排。

当实现发现要求反转依赖、改变权威所有者、修改正式知识路径或削弱不变量时，只暂停受影响的产品动作；先更新对应 ADR、架构或 Contract，再继续编码。无关的实现工作和文档整理不应被这些冲突机械阻塞。
