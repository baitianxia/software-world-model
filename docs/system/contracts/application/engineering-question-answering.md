# Engineering Question Answering

## Purpose and scope

本契约定义 `ENGINEERING_QA_ADAPTIVE_INVESTIGATION@3`：默认工程问答从 exact 软件世界模型取得持久的系统认知，由独立 Investigation LLM 根据原问题和每一步调查结果自适应决定下一步来源调查，再由受控 Source Broker / Retrieval Worker 执行。调查结束后才密封 Question Evidence Package，Answer 与 Reviewer 在隔离新上下文中只使用该包完成回答与审核。`@3` 在原 checklist 之下增加逐证据的 material observation closure，防止宽泛检查项被一个代表性事实伪闭合。

软件世界模型是软件系统在精确 Scope、Context、Schema 和 Snapshot 上持久、版本化、可验证、可更新的外部认知模型，独立于任何 LLM 会话或隐藏状态。它不是手册、地图或缓存；这些只是面向人、UI 或特定任务的投影。本契约改变的是问答使用认知和来源的方式，不改变世界模型的定义、正式知识路径或 `WORLD_MODEL` 的 Source-off 语义。

`ENGINEERING_QA` 是独立 Application 用例，不是 `WORLD_MODEL` 的回源分支，也不是 Knowledge Gap 后静默调用 `DIRECT_INVESTIGATION`。严格世界模型问答和直接调查继续由各自契约拥有。

## Ownership

- Application 拥有 immutable Engineering Question Request、Question Understanding Revision、Question Checklist、World Model Cognition Context、Investigation Attempt、Evidence Ledger/Revision、Question Evidence Package/Revision、恢复决定和不可变 Result。
- Knowledge Use / View 拥有 exact Snapshot 的正式查询结果、Coverage、Conflict 与 Unknown；它不拥有来源权限，也不决定调查是否结束。
- Question Understanding LLM 只提交对原问题的结构化理解 Proposal；初始 Investigation LLM 只提交 Investigation Step 和 Finish Proposal；独立 Verification Investigation LLM 只针对 Reviewer 的具体 gap 提交新的自适应 Step/Finish Proposal。三者都不拥有来源操作、Ledger、Package、事实、权限或答案放行，后者不得复用初始调查或 Reviewer 会话。
- Source Broker 拥有 Proposal 的策略校验、registered operation 编译与单次执行授权；隔离 Retrieval Worker 只执行 Broker 已批准的 exact-revision 只读操作。两者都不拥有问题结论、Package 密封或答案。
- Response Control 拥有 Draft Revision、Review Attempt/focus/derived Decision、Verification Request、Authorization 和 Delivery。Reviewer 只提交 closed quality/checklist assessment、逐项 evidence-boundary assessment 与 typed Finding remediations；可信 Adapter/Application 派生 action/request。每个可交付 Draft 必须先经 fresh `COMPREHENSIVE` Review，再经另一个 fresh `EVIDENCE_BOUNDARY_CHALLENGE` Review；前者只能形成 provisional approval，Reviewer 不能执行补证或自行放行。

## Request and role boundary

1. Request 在任何 World Model 查询、来源读取或模型调用前固定 `ENGINEERING_QA`、protocol identity、original question、response language、exact repository/Binding/revision、source path/content allowlist、Binding-scoped versioned Source Profile ref/digest、World Model Snapshot/Read Set selector、registered operation set、访问权限、高安全资源熔断、Provider disclosure policy 和不可变请求摘要。Source Profile 由受信配置拥有 evidence class → path capability；模型、问题和来源内容不能创建或修改分类。`CURRENT`/`latest` 只能在入口解析一次；开始后不得切换模式、revision、Scope、Source Profile 或 Source Target。
2. Question Understanding 必须保留原问题全文以及全部条件、比较、关系和输出约束，并记录 goal、audience、受控 `DIRECT / USER_VISIBLE_EXPLANATION / IMPLEMENTATION_DETAIL` 抽象层级、material conclusion checklist、evidence needs、`required_evidence_classes`、`required_evidence_paths` 和响应语言。它必须选择满足原问题的最低细节级别，并把可独立支持与明确要求保留未知的结论拆成不同 checklist item，使每项能形成单一一致的 outcome；流程/生命周期问题的 checklist 必须把用户可见阶段、成功/失败结果、重要状态变化以及持久化、审计、缓存、通知或外部交互等 material side effect 分成独立项，不能用类、方法、调用顺序、返回值或一个状态变化替代这些结论。`required_evidence_classes` 是回答 checklist 直接需要的最小、去重、受控 retrieval class 集合，不是当前 Profile registered class 的副本；`required_evidence_paths` 是 1—4 个去重、exact、回答决定性结论前必须完整读取的仓库相对文件，是 mandatory minimum 而不是所有授权文件、候选文件或完整调查计划的副本。该上限与 Slice1 当前 12-call initial-investigation fuse 共同保证 4 次 direct mandatory READ/PARSE + 1 次 FINISH 后仍有 7 次自适应余量；可选佐证不能占用 mandatory capacity，也不能以调用预算为由删除 material checklist 或 required class。多机制、参与者或检查面必须在这个最小集合内选择各决定性机制自身实现，不能只选 caller、registration 或 wiring；问题同时跨 build declaration 与 runtime behavior 时，不能把全部 mandatory capacity 用于重叠 module declaration 而漏掉决定性实现，可选构建/文档佐证留给 mandatory closure 后的自适应调查。若问题要求经过多个 stage 后才产生的外部 HTTP/API status、error category 或 response body，最小决定性集合还必须选择实际拥有该下游输出的 response/exception mapper 完整实现；上游空认证上下文、异常、deny decision 或自定义 handler registration 只能证明局部状态或选择关系。若 mapping owner 不在授权范围或不可用，外部结果必须保留为独立 unknown，transport status 与 application/response-body error code 也必须分成不同结论。每个 required path 必须位于 immutable Request allowlist，由绑定 Source Profile 唯一解析到一个 registered class，且该 class 同时出现在 required classes。实现行为、条件、状态变化、结果或失败路径需要 `SOURCE`，仓库记录的用途/行为需要 `REPOSITORY_DOCUMENT`，依赖、插件、profile 或 toolchain 需要 `BUILD_CONFIGURATION`，问题明确要求测试本身或测试断言的行为才需要 `TEST`；不能仅因某类证据可用、可作可选佐证，或用户要求“可核对依据”就引入 TEST、日志、配置等额外 material need，源码 locator 已可作为 source-behavior claim 的核对依据。抽象层级约束交付答案的表现形式，不缩窄调查可使用的证据类别；工程问题询问 feature/flow/lifecycle/authorization/failure behavior 时，即使答案保持用户可见，Question Understanding 也必须保留 exact implementation behavior 的 Source evidence need，不能用“避免实现细节”的表现约束排除实现证据。模型不得把问题改写为更容易回答的问题；Application 校验路径权限与 class 绑定，不以当前证据删除尚未解决的 Need。

   配置占位符或 injection annotation 只证明 key 与 injection point；具体 header、prefix、port、URL、secret、profile 或其他 runtime value 是独立结论，必须由获授权的直接 value evidence 支持。parameter、return type、import、caller 或 registration 只证明可见签名/关系，不能证明未挂载 DTO 的 fields/validation 或未挂载 handler 的 output。缺少实现或配置值 evidence 时，Question Understanding 必须把该 detail 保留为可独立处置的 unknown，不能用框架惯例补齐。

   问题要求用户 start/call/use/integrate/diagnose 系统时，checklist 必须是 operational 而非 inventory-shaped：按适用范围分开 prerequisite 或 build/start 动作、首个请求及输入、返回值、前一步输出到下一步输入的 handoff、结果/失败和仍未知的运行参数。依赖、类、filter 或 handler 清单不能替代动作与输入/输出交接。
3. World Model Cognition Context 必须来自固定 Read Authority，至少绑定 exact Scope、Context、Schema、Snapshot/Read Set、source revision、typed Result、Entity/Relation/Behavior/Constraint/State、Coverage、Support、Conflict、Unknown、locator 与 digest。它是世界模型对当前任务的只读认知投影，不是另一个事实库。
4. World Model source revision 与 Request repository revision 必须 exact 相等。显式版本比较问题可以使用分区的 exact Read Set，但每个分区必须独立绑定对应 Source revision。未对齐或无法证明相等的 Result 只能标记 `UNALIGNED_REVISION` 并作为候选导航，不能直接支持当前 revision 的 Claim；相关内容必须在 Request revision 上重新核实。
5. Question Understanding、Investigation、Answer 和 Review 是分离角色。每个模型步骤使用精确输入 allowlist、closed output schema、Strategy/Prompt 身份和独立收据；输出收据必须绑定当前 role、fresh role context、input Manifest digest 与 output schema ref/digest。Review 角色在同一 closed output schema 下使用受信 `COMPREHENSIVE / EVIDENCE_BOUNDARY_CHALLENGE` focus；两个 attempt 必须使用不同 fresh context，后者不能继承或假定前者的 provisional approval。每个投影 lead 具有 Application-owned 稳定 `challenge_id`；comprehensive 输出必须返回空 challenge assessment，challenge 输出必须对 required ID 恰好逐项返回 evidence scope、Draft scope 与受控 disposition。每个非 passing assessment 还必须绑定同一输出中、其单一 Claim 属于该 exact challenge scope 的 Finding；Finding code 存在或 Claim 属于另一个 challenge 都不能满足绑定。模型只提交 schema 允许的语义字段，request/package/draft digest、attempt、focus、Ledger ID/generation/revision/prefix 等权威坐标由可信适配层从当前状态补入并由 Application 重验，不能由模型回显取得权威。Provider 会话记忆、隐藏 rationale、未密封工具结果或上一角色私有输出不得成为正式输入。
6. 在任何真实 Provider dispatch 前，Application/Gateway 必须验证 current exact Provider、model、endpoint、configuration、role、secret reference、允许外发的 Cognition Context/Ledger/Package 字段或片段、redaction 和完整 input digest 已单独密封并授权。用户级 run grant 必须绑定 exact immutable logical question/evaluation subject、Session 预授权的 Ark→DeepSeek ordered route、Prompt/output contract、角色集合、primary + fallback 最坏总调用上限和授权消息；它本身不能直接 dispatch。每个运行时动态形成的角色输入还必须按 provider attempt 密封完整 Gateway Manifest、所有 model-visible 字段路径与片段摘要、payload bytes、schema/Prompt 和 full input digest，并由受信边界把 run grant 收窄为恰好一次 dispatch 的 role disclosure authorization。Gateway 在 credential resolution/HTTP 前独立重验同一 run grant、root Request、完整 role payload、Provider/qualification 和由前一结构化 Result 决定的角色/focus 顺序：Answer 后只允许 comprehensive Review；其空 Finding Result 只允许 evidence-boundary challenge；challenge 空 Finding 才进入 terminal。真实 Web launcher 还必须在 listener 前证明自身从 clean exact product candidate 加载，绑定 published Bundle semantic/file digest、exact Source/Profile/Request/run authority，并先密封零分派 launch receipt；退出时按 logical question/provider attempt 密封逐角色、Gateway 与 transport terminal audit。任一授权、输入或 Result 只能消费一次；同一 Provider dispatch 后异常、outcome unknown、identity drift 或 replay 不 retry。仅当 primary attempt 已密封为无 authorized answer 且属于 ADR-017 的 Provider/model reason，Application 才可透明创建一次 fallback attempt；它从 original question 与 exact Cognition 重跑全链，不复用前一 attempt 中间态。Secret value、secret reference 和授权 receipt 都不得进入模型消息。历史开发、Conformance、Capability、Product 或浏览器授权不能推导这次来源内容披露。
7. 持续本机 Web 必须在 listener 前密封升级后的 Engineering QA Session Authority：固定 clean exact product candidate、loopback origin、工程/
Binding/revision、World Model Read Authority、Source Profile/global + class allowlist、registered operations、Ark→DeepSeek ordered route 及每条 route 的 model/endpoint/
configuration/qualification/secret reference/disclosure scope、角色 Prompt/schema、redaction、有效期、每题及整会话 logical-question/provider-attempt/dispatch/bytes/wall-time 熔断和
`NOT_EXECUTED` Production 状态。Session Authority 只授权这个闭合边界，不授权未知问题或任何 dispatch。页面必须显示外发边界；用户
点击提交时，受信 ingress 密封 exact UTF-8 question bytes/digest、session authority digest、提交时刻和 disclosure acknowledgement，
并签发 server-owned unique logical-question/request identity。System Owner 只能由该 `Question Submission Receipt` 与固定模板编译 exact Request 和
per-question run grant；客户端不得提交 request ID、grant、Provider 或来源参数。每个 provider attempt 与动态角色输入继续按第 6 条收窄为 one-use 授权。
重复 receipt、会话漂移/过期/总熔断耗尽必须在 credential/HTTP 前拒绝；单题失败不停止 listener，且不得污染或复用另一题的 Ledger、
Package、Review、Citation 或授权。浏览器问题 POST 必须在 receipt 前满足 exact loopback same-origin、`application/json` 和可用时的
`Sec-Fetch-Site: same-origin`；CORS 响应不可读不能充当副作用防护。工程、revision、Source/Provider 边界变化必须停止并新建 Session
Authority。

## Adaptive investigation and Evidence Ledger

1. 初始 Investigation Step 只读 immutable original question、已接受的 Question Understanding/Checklist、受信 Request 控制字段和 World Model Cognition Context。后续 Step 还可读取 Application 密封的当前 Evidence Ledger prefix。世界模型为 Investigation LLM 提供系统认知起点；零结果、无关内容或 Coverage 不足是显式认知状态，不得阻断原问题驱动的受权调查。
2. Investigation LLM 每一步只能提出一个版本化 schema 中注册的 `search`、`read`、`parse` 或 `FINISH` Proposal，并说明它对应的 Checklist/evidence need、预期消除的未知及与当前 Ledger 的关系。每个动作的 `checklist_item_ids` 必须复制一个或多个当前输入中的 exact、unique checklist ID，不能用空数组解除问题绑定；`basis_entry_ids` 同样必须 non-empty、unique 并包含 Application 投影的 exact `required_basis_entry_id`。Provider-facing Schema 与 Domain 必须对这两个非空/唯一约束一致，Schema 通过不能放宽 Domain。Proposal 可以根据前一步 Result 改变后续方向，实现真正的自适应多步调查；它没有直接工具句柄，不能执行操作、修改 allowlist/revision/预算、删除 Need 或把 `FINISH` 变成平台事实。
3. Source Broker 必须把 Proposal 和其中的 evidence class 当作不可信建议，重新解析 locator、拒绝模型命令和 URL、验证 exact Binding/revision/regular-file/global allowlist/Source Profile identity/class-specific allowlist/registered operation/参数/remaining fuse，并编译 caller 不可伪造的 Source Operation。普通 read/parse locator 必须由当前 Ledger 的 search Result 签发且属于相同 class capability；对于 Question Understanding 已选择且由 Application 验证为 Request allowlist 成员、又由 Source Profile 唯一解析到一个 class 的 mandatory path，Broker 可以签发不含内容的 direct opaque locator。该 locator 必须绑定 exact Request digest、Investigation attempt、Source Profile digest、class 与 path，并在每次编译时重建 identity、重验 global/class allowlist；模型只能复制当前 role input 的 reference/evidence class，不能提交或扩大 path authority。非法、无进展、重复或越界 Proposal 形成明确 Decision/Failure，不获得 Worker dispatch。
4. Retrieval Worker 只能执行 Broker 已批准的 list/search/read/parse 等只读 Source Operation。源码、仓库文档、构建/运行配置和测试是同一受控来源面的不同 evidence class；平台按显式注册、版本化的 Source/Profile capability 解析，不按题目、工程、关键词或模型声明分类。每个 operation 必须绑定 exact Profile ref/digest、完整 class-specific allowlist 和 expected Result modality，Worker 重验 Binding/Profile 后只读取 global allowlist 和 class allowlist 的交集，并只能产生 Profile 为该 class + operation 注册的 modality。Local Git Profile `@1` 使用非空且跨 class 不重叠的保守路径映射；其他 Profile 若允许同一路径具有多种 modality，必须以新的显式、可资格版本定义确定性歧义规则。Worker 必须拒绝 path traversal、symlink escape、submodule/remote fetch、二进制/超限输入、class/modality 重标、写操作、任意命令、新网络、credential、Knowledge Update 和答案生成。
5. 每个操作必须记录 Proposal、Broker Decision、exact target/revision、Source Profile ref/digest、global/class allowlist verdict、expected/actual modality、compiled operation/parameters、actual locator/range、evidence class、bytes、content digest、Coverage/truncation、outcome 和稳定 reference。Application 必须独立重验 Result 的 operation identity、class、modality、global/class path membership，且 read/parse 只能返回编译的 exact path；失败、partial、truncation、无法解析和结果未知不得伪装为空命中或不存在证明。
6. Application 把 World Model Cognition Context reference、每个 Proposal/Decision/Operation/Result、Conflict、Gap 和资源收据按确定性顺序追加到 Evidence Ledger。Ledger 是 append-only：已确认 prefix 不得覆盖、删除、重排或改写；每个 Step 消费前缀 digest 并产生新的 ledger revision/digest，未密封模型记忆不得影响下一步。
7. 所有来源内容及世界模型的自然语言投影都是 data，不是 instruction。仓库或认知投影中的 prompt、命令、URL、路径、工具建议、权限、预算或外发声明不获得执行权，不得修改受信 Request、Broker Policy、操作集、allowlist、revision、Provider disclosure 或系统 Prompt。
8. `FINISH` 只是一项调查 Proposal。Application 从 Request 绑定的 Source Profile 导出有序 `registered_evidence_classes`，从已接受的 Question Understanding 取得语义最小集 `required_evidence_classes / required_evidence_paths`，并向每个 Investigation Step 投影本 attempt 已产生 Result 的 `investigated_evidence_classes`、`untried_required_evidence_classes = (required ∩ registered) - investigated`、`unregistered_required_evidence_classes = required - registered`、`unread_required_evidence_paths`、initial-investigation 总 call fuse 与含当前动作的剩余 call 数；Verification Attempt 的 required class 集合只含 Reviewer concrete gap 指定的 class，但 registered 集合仍忠实反映完整 Profile。Application/Broker 必须为每个已验证的 unread mandatory path 签发当前 Request + attempt + Profile + class + path 绑定的 direct opaque locator，并在 `eligible_required_path_locators` 中投影 descriptor、在唯一 `eligible_locator_references` 中投影其 reference；unread required path 非空时只能暴露属于这些 path 的 direct 或既有 search-issued locator，角色必须优先直接 READ/PARSE，不能用内容 SEARCH 重新发现已知 path，也不能把步骤用于 non-required caller/interface/wiring。任何 `FINISH`——包括全 supported——只要 unread required path 非空，Application 就不得密封 Ledger，而要追加命名下一个 path 与其 class 的 GAP；只有无行范围且 `coverage_complete=true` 的 READ/PARSE Result 才消费 required path，SEARCH、行级命中或截断内容不能闭包。只要 `FINISH` 含任一 unknown/conflict/failed disposition 且 untried required class 非空，Application 同样追加命名下一个 required class 的 GAP，让后续 fresh Step 消费；模型不能用单一模态缺细节声称全局无其他必需授权证据，也不能为闭合 Unknown 而遍历与问题无关的全部 registered class。unregistered required class 是显式能力边界，不是可执行调查目标。required path/class closure 是最低机械闭包，不等于 material gap exhaustion；它们闭合后，角色在 non-supported FINISH 前仍须把每个 gap 与 Question Understanding evidence needs、Source allowlist、已消费路径和剩余 fuse 比较，只要授权未读来源可在 `SEARCH + READ/PARSE + FINISH` 预算内缩小缺口就必须继续调查，不能因同 class 已读过其他文件而结束。Application 只有在 Proposal 绑定当前完整 Ledger、authorized checklist scope 中每项都有 supported/unknown/conflict/failed disposition、required-path closure 和 non-supported disposition 的 required-class closure 均已闭合、没有未记录操作且 Ledger 结构有效时才可结束调查；语义证据是否足够仍由 Answer/Reviewer 检查。Initial Attempt 的 authorized scope 是完整 Question Checklist；Verification Attempt 的 scope 只有 `verification_request.checklist_item_id`，每步和成功 FINISH 均不得绑定其他项。Provider-facing FINISH closed output 只允许一个必填 `finish_dispositions` 数组；SEARCH/READ/PARSE 时该数组为空，FINISH 时 authorized scope 中每项必须恰好出现一次。因此 Initial FINISH 返回全量 disposition set，Verification FINISH 只返回一个 gap delta。每个 item 使用 outcome-tagged closed variant：`SUPPORTED` parent 只允许 `PROCESS_STAGE / OUTCOME / STATE_CHANGE / SIDE_EFFECT` child observations，`UNKNOWN / CONFLICT / FAILED` parent 只允许 `LIMITATION` child observations。Provider 不再重复声明 parent `evidence_references`；可信 adapter 仅按 child observations 的 Provider 顺序对其 exact references 做稳定 first-occurrence union，并以该结果构造既有 Domain parent closure，不改写 outcome、explanation、observation statement/kind/reference。Application Domain 继续独立拒绝 duplicate、越过 authorized scope、混类、非 exact-once、错误证据分区或引用不闭合输出。每个 disposition 必须把完整引用内容中与原问题及受控抽象层级相关的事实拆成 1—16 条原子 material observations，完整 Package 全局最多 64 条，并逐条绑定实际需要的 admissible evidence references。一个宽泛总结或代表性效果不能替代不同阶段、结果、状态变化、持久化/审计/缓存/通知写入、外部交互或失败结果；不得把与该 checklist 无关的覆盖担忧附加到已支持 disposition。setup 说明只支持 setup，依赖、注册、声明或 wiring 只支持该关系；它们不能替代被委托组件内部的条件、比较、状态变化、结果、失败语义或相邻应用流程。上游空认证上下文、抛出异常或 authorization deny 同样只支持该局部状态，不能在没有下游 response/exception mapper 完整实现时推出最终 HTTP/API status、error category 或 response body；自定义 handler registration/class name 只证明选择关系，不能用 framework default 补齐其输出。transport status 与 application/response-body error code 必须分别取证。原问题询问 how/why/条件/排障行为时，若已授权且预算可达，Investigation 必须完整读取能表达每个决定性机制行为的实现证据，否则只能形成诚实的 non-supported disposition。Source Profile allowlist 中列明的路径属于已授权来源范围，模型不得把它声称为未授权；有 material Broker locator 时应先 read/parse。Application 重建稳定 observation identity，拒绝重复、跨 checklist 或引用不闭合的观察。无合法下一步且全部 required closure 已闭合但仍有缺口时可以密封 limitation-bearing Package，不能伪造完整性。

配置占位符或 injection annotation 只支持 key/injection point，不能支持具体 runtime value；parameter、return type、import、caller 或
registration 只支持可见签名/关系，不能支持未挂载类型的 fields、validation 或 output。这一证据边界同时约束 Initial/Verification
Investigation、Answer 与两个 Review focus。challenge 判断 imported type 是否已挂载必须比较完整 package-qualified import identity；
另一个 package 中的同名 Java 文件不能消除该 lead。

## Package formation and epistemic boundary

1. 调查结束后，Application 从 immutable Request、Question Understanding/Checklist、World Model Cognition Context、完整 Evidence Ledger、所有 typed Source Result、Coverage、Conflict、Unknown、locator 和资源收据密封 Question Evidence Package。调查过程中不存在供 Answer 使用的临时 Package。
2. 每个 Package 保持一个不可变身份与 seal，但必须包含两个显式分区：
   - `support/citation`：仅包含按 modality、Context、Coverage 与 Support 校验通过的 admissible entries；只有该分区可以支持肯定 Claim 与 Claim Citation；
   - `boundary/audit`：必须保留 Boundary、Gap、Failure、Partial、Conflict、Unknown、Rejected Decision 和 Resource Receipt；它可以约束结论或形成带标签的 Boundary/Audit Reference，但不得支持或引用为肯定 Claim。
3. 每个 Package 至少绑定：
   - Package/Revision ID、protocol identity 与 digest；
   - immutable Request、original question、Question Understanding 和 Checklist digest；
   - exact repository/Binding/revision、Source Profile ref/digest、World Model Read Authority/Bundle digest 和 source-revision alignment verdict；
   - Evidence Ledger ID/revision/final prefix digest 及有序 Proposal/Decision/Operation/Result references；
   - 每个 entry 的 origin class、modality、Context、locator、content/result digest、Coverage/truncation、Support、Conflict/Unknown 和 disclosure class；
   - 每个 Checklist disposition 的原子 material observations、稳定 observation identity、observation kind 与 evidence references；
   - 未满足 Checklist item、失败/partial/unknown outcome、资源收据、package manifest 与 seal digest。
4. Package 是当前 Question Revision 中 Answer 和 Reviewer 唯一允许消费的证据与边界集合，但“进入包”不等于“可支持肯定结论”。未进入当前 Package 的 Source 内容、搜索印象、模型参数知识、会话记忆、rationale、旧 Package 或旧 Review 均不能支持结论。
5. Package seal 只证明内容集合的身份、完整性、顺序、provenance、revision 和未被篡改，不把内容变成真：search candidate 只证明命中，源码/配置只证明该 revision 的静态实现，文档只证明记录的用法或意图，测试只证明静态预期或已密封执行观察，World Model entry 只证明已发布认知及其 Context/Coverage，模型 Proposal 不构成事实。肯定 Claim 仍必须逐项绑定 `support/citation`；`boundary/audit` 只能说明边界、失败、冲突或未知。
6. 无显式受控解析规则时，任一 origin class 不自动胜出；不兼容内容保留在 `boundary/audit` 为 Conflict，不能被 Investigation、Answer 或 Reviewer 静默消解。Question Evidence Package 不是 Fact、Inference、Snapshot member 或跨任务正式知识。
7. Package 密封后不可追加、替换、重排或改写。任何补证必须以旧 Ledger 作为不可变 prefix 创建新 Ledger Revision，追加新的完整调查记录，再密封具有新 ID/Digest 的完整 Package；不得修改旧包。成功 Verification FINISH 的单 gap delta 由可信 Application 按 predecessor Package 原顺序替换唯一目标 disposition，非目标 disposition 对象/digest 必须原样保留；目标缺失/重复、Request/Package identity 不同或 delta 非单项均失败关闭。该 merge 只形成 successor Package，不是原地修改 predecessor；失败关闭的 Verification 不执行 delta merge。Verification 可以复用 predecessor 的 admissible support，但其非支持 delta 不得引用 predecessor Package 的任何 boundary；Application 必须从 boundary eligibility 中机械排除它们，并显式提供本次 Verification Request 的唯一 gap boundary。每个 `UNKNOWN / CONFLICT / FAILED` material observation 都必须保留该 exact gap reference，可同时引用本 attempt 新产生的 boundary；用旧 cognition unknown、search candidate、rejection 或 gap 冒充当前缺口必须失败关闭。

## Answer, independent review and recovery

Answer closed output 必须由一个且仅一个必填 `direct_answer` 对象和一个 follow-up `claims` 数组构成；后者的 schema 禁止
`DIRECT_ANSWER`。两处分别以 closed variant 约束 kind/content role：affirmative direct 或 limitation direct 只能出现在
`direct_answer`；follow-up 只允许 affirmative `USER_VISIBLE_PROCESS / IMPACT_OR_SIDE_EFFECT / IMPLEMENTATION_EVIDENCE` 或
limitation `LIMITATION`。混合 Package 的 direct answer 必须是只概括 supported checklist 的 affirmative summary，所有
unknown/conflict/failure 进入末尾 limitation follow-up；只有全部 checklist 都 non-supported 时 direct answer 才能是 limitation。

Gateway 必须保留原始 Provider Answer output 与 digest。可信 Answer adapter 在构造 Domain Proposal 前，只能对 follow-up claims 按
`USER_VISIBLE_PROCESS → IMPACT_OR_SIDE_EFFECT → IMPLEMENTATION_EVIDENCE → LIMITATION` 做稳定的展示顺序归一化；同一 role 内的
Provider 顺序以及 claim ID、kind、role、checklist/observation/evidence links 和文本都不得改写，唯一 `direct_answer` 仍固定首位。该
归一化不修复非法 role、kind/role 混类、coverage、证据分区或正文语义错误；Application 对归一化后的 Proposal 继续执行全部 fail-closed
不变量，并拒绝任何绕过 adapter 的乱序 Proposal。raw output 与 canonical Proposal 必须分别可审计。

Reviewer 的完整性审计必须逐个检查 flow/lifecycle 相关 full-content entry 的成功/失败分支以及持久化、审计、缓存、通知和外部交互；
对多机制/检查面，还必须确认每个决定性机制自身的实现已进入 Package。caller/configuration/wiring 只证明接线，不能证明被委托行为。

Application 必须从当前 Package/Draft 机械投影 `evidence_boundary_challenges` 作为第二 Review 的审计 leads：默认正文引用的内容若只含
配置占位符，投影 key、entry 与相关 Claim；默认 Claim 出现具体 HTTP status literal 而其引用内容没有该 literal 时，投影 Claim/status；
Draft 提及同 application import、但相应实现未进入 Package 时，投影 type、importing entry 与相关 Claim；每个被默认正文 Claim 引用的
full-content Java support entry 还必须各自投影 `FULL_CONTENT_MATERIAL_EFFECT_SCAN`，逐 entry 检查 persistence write、audit write、
cache mutation、notification 与 external interaction，并同时投影该 entry 当前已经拥有的 exact Application material observations。
该 observation 归属必须先由 exact support entry ID 解析出其 `source_reference`，再匹配 material observation 的 evidence references；
不得把 `support_entry_*` 与 `retrieval_item_*` 两个 ID 域直接比较，也不得让 challenge view 与 Application Gate 各自维护不同映射。
每个具有默认正文和实际引用 Package entry 的 Draft 还必须投影一个
`ORIGINAL_QUESTION_FULFILLMENT_SCAN`，绑定全部 default Claim 与引用 entry，并独立核对 direct user goal、ordered user actions、
input/output handoff、known/unknown boundary 和 material outcomes；对 startup/call/use/integrate/diagnose 问题，组件或依赖清单不能
冒充可执行步骤。该投影不自动判错，也不创建 evidence truth 或 Source authority；空 effect scan
必须说明已检查且没有 material effect，非空 scan 必须把每个 effect 映射到 exact default Claim。Reviewer 仍须区分用户陈述的现场症状、
合法的签名/registration 说明与错误的配置值、DTO fields、handler output、下游 status 扩张或 material effect omission。

每个 Draft 先运行 fresh `COMPREHENSIVE` Review；只有 finding-free provisional approval 才运行另一个 fresh
`EVIDENCE_BOUNDARY_CHALLENGE` Review。challenge 必须按稳定 `challenge_id` 逐项分别陈述 cited full content 能证明的最大范围与 exact Claim
实际断言范围，再返回 `WITHIN_EVIDENCE_BOUNDARY / DRAFT_EXCEEDS_EVIDENCE_BOUNDARY / DRAFT_OMITS_MATERIAL_EFFECT /
DRAFT_OMITS_MATERIAL_REQUIREMENT`；后两种专用 disposition 只能用于各自的 material-effect / original-fulfillment challenge kind；错配、漏项、重复、未知 ID 或
comprehensive 提前处置都在 Application 授权前失败关闭。每个非 passing disposition 必须绑定同一输出中作用于该 exact challenge
`default_claim_ids` 之一的 Finding；只有同一 Claim 同时属于每个被绑定 challenge 时才可复用 Finding code。getter 调用只证明 caller 调用
并使用返回值，不证明未挂载类型含同名 field、wire property 或 validation。任一 focus 的 rewrite、missing evidence 或 reject 都沿既有 typed
remediation 状态机处理。`DRAFT_OMITS_MATERIAL_EFFECT` 还必须列出 exact omitted-effect statements 并选择 closed omission layer：
`APPLICATION_PACKAGE` 表示 effect 不在该 entry 的投影 observation 中，只能绑定同 evidence class 的
`INVESTIGATE_MISSING_EVIDENCE`；`DEFAULT_DRAFT` 表示 effect 已精确存在于该投影，只能绑定 challenged entry 的
`REWRITE_WITH_EXISTING_EVIDENCE`。空投影存在非空 omission 时 `DEFAULT_DRAFT` 不可能；同一扫描同时发现两层 omission 时，当前轮只返回
不在 Application observation 投影中的 effects 并优先形成 successor Verification，后继 Package 再审核剩余 draft-only omission。
Application 重算 statement membership、entry/class 与 remediation，错误层级失败关闭；只有所有
challenge 都在边界内且 Finding 为空的 challenge approval 可以授权 Delivery。

1. Answer 使用隔离的新上下文，只读 original question、accepted Question Understanding 和一个密封 Package；没有 Repository mount、Source/World Model Tool、Evidence Ledger write port、shell、网络、credential、Reviewer 输入、Investigation 私有输出或 Provider 会话历史。
2. Answer 的每个 Claim 必须声明 `DIRECT_ANSWER / USER_VISIBLE_PROCESS / IMPACT_OR_SIDE_EFFECT / IMPLEMENTATION_EVIDENCE / LIMITATION` 之一，并绑定一个或多个 accepted material checklist item。每个表达 Package 实质事实的 Claim 还必须绑定其文本实际表达的 Package material observation identity，但有两个受控空-link 例外：答案末尾只陈述 evidence scope/coverage boundary 的 `LIMITATION` Claim 可以使用空 observation-ID 集合且只能引用 `boundary/audit`；有 support 的 affirmative `DIRECT_ANSWER` 也可使用空集合作为简短摘要，但其每个 checklist 必须为 SUPPORTED、每个摘要事实必须由后续带 observation link 的默认 Claim 完整展开，且摘要本身不取得 observation coverage。前一例外不得承载 affirmative fact 或错绑 supported observation；后一例外不得引入后续 Claim 中不存在的条件、结果、状态变化、副作用或 limitation。恰好一个 `DIRECT_ANSWER` 必须排首位；它可以是有 support 的 affirmative，也可以在真实边界下成为直接、诚实且仍绑定对应 `LIMITATION` observations 的 limitation。

   默认用户可见正文必须恰好覆盖每个 Package observation 一次；`DIRECT_ANSWER` 保持简洁，后续用户可见 Claim 承载其余阶段、条件、结果与副作用，不得把同一 observation 在直答和分段中重复。每次 Answer 输入必须在原问题和大对象之前提供 exact material-observation coverage table，逐项列出 Application-owned observation ID、statement、kind、checklist 与全部 required Package evidence entry；初答和同包 rewrite 都必须逐项核对。收窄一个越界推断不得删除同一旧 Claim 承载的其他安全 observation，必要时拆分或重写 prose，但 ID、statement 语义和 evidence closure 仍须保留。Application 按 Claim 顺序构造默认正文：始终保留首次覆盖；后续 Claim 的 observation 若已被完整覆盖，则从默认正文投影到开发者详情；若只与既有覆盖部分重叠则失败关闭，不能静默拆句或丢弃新事实。默认隐藏的 `IMPLEMENTATION_EVIDENCE` 可复用已经由其他用户可见 Claim 完整覆盖的 observation 提供开发者细节；若它是一个或多个 material observations 的唯一 Claim carrier，则必须进入默认正文，不能把用户明确要求的核对依据只藏在开发者详情。若 implementation Claim 与既有用户可见 Claim 的 observation 只部分交叠，仍须失败关闭，不能拆句或静默丢弃重复部分。

   startup/call/use/integrate/diagnose 类问题还必须把 supported observations 组织成可执行用户序列，显式连接 material output 到下一动作输入，并把具体已知值与 configuration-backed unknown 分开；参与组件清单不构成 actionability。

   Application 还必须拒绝角色乱序、任一 checklist 或 observation 未覆盖、用户可见 observation 部分交叠、空-link affirmative summary 覆盖 non-supported checklist、observation 只出现在默认隐藏的实现详情、supported disposition 没有 affirmative Claim、non-supported disposition 没有 limitation Claim、observation 跨 checklist，或 Claim 未引用该 observation 所需的全部 Package evidence entry。流程阶段、结果、重要状态变化和副作用是用户可见结论，不得降格为可选实现细节。实现证据仅在原问题明确请求或支持 material conclusion 所需时产生；`USER_VISIBLE_EXPLANATION` 默认隐藏 observation 已由其他可见 Claim 完整覆盖的实现证据，但保留 uniquely material 的简洁实现核对依据；`IMPLEMENTATION_DETAIL` 默认展开全部实现证据，不使用固定标题或字数比例。每个实质肯定结论必须绑定当前 Package `support/citation` 分区中一个或多个具有实际 Support 的 entry，且不得扩张其 Context、modality、Coverage 或时序。Claim Citation 必须回到该分区的稳定 locator/digest；`boundary/audit` 条目只能解释 limitation、failure、conflict 或 unknown，不能支持肯定结论。答案文本、模型 rationale、搜索命中或 Package seal 本身不是证据。
   Answer 不得把 Package 中的上游局部状态、异常或 deny observation 改写为外部 HTTP/API status、error category 或 response body，除非所链接 support evidence 包含实际拥有该下游映射的完整实现。缺少 mapping-owner evidence 时，正文只能陈述已支持的局部机制并把外部结果保留为 limitation；custom-handler wiring 不能替代 handler output，也不能混同 transport status 与 application/response-body error code。
3. 无法推出的内容必须表达为用户可理解的 unknown/limitation：说明已能确认、尚不能确认、缺失的具体证据及影响范围。不得向普通用户机械平铺 operation、ledger、candidate、recall、Profile、authority、proof 或内部 Review 文本。
4. Reviewer 使用另一个隔离的新上下文，只读 original question、accepted Question Understanding、当前 Package 和 Draft；它不继承 Investigation/Answer 会话、rationale 或旧 Review。Reviewer 必须先从 immutable original question 独立形成 material body，Reviewer 还必须在 Package 中识别拥有该下游输出的 full-content response/exception mapper；上游空认证上下文、异常、deny decision 或 handler wiring 只证明局部状态/选择。缺少 owner implementation 时必须把外部结果判为 unsupported，不能自行提供 framework default；若该结果属于 original question/accepted checklist 的 material conclusion，则形成 evidence-gap Finding，若它只是 Draft 自行扩张的非必要细节，则使用当前 Package evidence 删除、收窄或改写，不得借 Reviewer 新增范围扩大调查。宽泛 checklist 能容纳一个 Draft detail 不等于 detail 本身 material；删除该 detail 后仍完整回答原问题/checklist 时必须选择同包收窄。对于已由 bounded Verification 调查、在 successor Package 中以当前 gap boundary 密封为 non-supported disposition 的 `verified_gap_outcome`，只要 Draft 诚实保留 limitation 且未暗示缺失的肯定结果，该未知本身完成当前授权下的 material boundary，`material_completeness` 可以 PASS，Reviewer 不得再次请求同一缺证。这不豁免其他 supported 本地机制或不同 checklist gap。同一局部条件被同时赋予 authentication-failure 与 authorization-denial 结果，或 transport status 与 application/response-body code 被混同，也必须令一致性检查失败。随后分别对 direct answer、abstraction fit、material completeness、claim consistency、implementation-detail budget 返回 `PASS / FAIL`。它还审核逐结论正确性与支持、条件/顺序/异常/冲突/未知、相关性、可读性和可操作性。
   `verified_gap_outcome` 的资格只来自 `VERIFICATION_REQUEST` 密封的 typed `VERIFICATION_GAP`；Initial Investigation 产生的普通 `GAP`
   不得因为后续 Package revision 存在就被误投影为已穷尽终态。
   `ORIGINAL_QUESTION_FULFILLMENT_SCAN` 必须直接从 original question 重建交付目标，而不是采用既有 checklist 或把 Draft 组件名回显当作覆盖。若当前 Package observations 已足够但正文漏掉动作、输入/输出交接、known/unknown boundary 或 material outcome，Reviewer 使用 `DRAFT_OMITS_MATERIAL_REQUIREMENT` 与同包 rewrite Finding；若 cited full content 已证明所需事实而 Application observations 缺失，则同时报告 Application omission 并走 successor gap delta。
   full-entry effect challenge 不能用同一 file 的另一个 observation 冒充缺失效果已经进入 Package；每个 omitted-effect statement 都必须和
   该 entry 的 exact observation projection 比较并输出 `APPLICATION_PACKAGE / DEFAULT_DRAFT` 层级。前者即使 full content 已可见，也仍需
   successor Package 取得 Application-owned observation ID；后者才可同包改写。
   `APPLICATION_PACKAGE` 的 gap 必须请求把 challenged full-content entry 中已经可见的 exact helper call、cache invocation、write、

## Generality and knowledge reuse

Question Understanding、World Model Cognition Context、Investigation Proposal、Broker/Worker、Evidence Ledger、Package、Answer 和 Review 使用同一通用协议。核心代码、Prompt、UI 和评测不得按问题、项目、语言、框架、关键词、符号、约定文件名、fixture 或 Oracle 选择路由、来源、证据或答案。来源类型和语言解析差异只能由显式注册、版本化且通过资格的 Source/Profile capability 处理。

完成 Delivery 后，Application 可把高质量 Package 与已审核结论作为异步 Knowledge Update Proposal 输入。它不继承问答 Review 的正式知识资格，必须重新形成 Artifact/Evidence/Candidate，通过独立 Admission 并原子 Publication。同步答案不依赖该过程，更新成败不改变已交付答案；新的正式认知只在后续 exact Snapshot 中生效。
