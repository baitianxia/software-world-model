# Development Design Policy

Development Design 是当前编码输入，不是长期详细设计百科。它应当足以让人或 Agent 知道要改变什么、不能破坏什么、如何验证，并允许局部实现由代码和测试快速探索。

## 先体验方向，再夯实实现

凡是用户可以直接感知、且方向风险较高的产品变化，计划默认拆成四个阶段，顺序不得倒置：

1. **方向探针：** 用最小纵向实现贯通真实入口、核心交互和极少量代表性输入，尽快暴露答案形态、交互和职责分工是否正确；
2. **可用 Alpha：** 只做探针反馈要求的最小通用修正，立即用一组小而多样的输入和新的现场输入再次让用户判向；
3. **工程夯实：** 只有 Alpha 被明确确认后，才补齐完整契约、边界处理、回归、性能、可观测性和质量评估；
4. **正式验收：** 在实现稳定后执行隐藏输入、对照、现场问题和发布前 Gate。

低方向风险的小改动可以在 Proposal 中论证合并前两个反馈段；涉及新答案协议、新交互主线、新模型职责或其他容易“完整做完才发现方向错误”
的变化不得合并。无论是否合并，用户可操作的真实结果都必须先于与方向判断无关的全面夯实。

方向体验版不是验收版，不得声称完整、稳定或可生产使用，但始终必须遵守数据/源码授权、只读和写入权限、Secret 隔离、外部调用
披露、失败不伪造成功等不可推迟的安全边界。除非某项工作是安全运行或判断核心方向的必要条件，不得把完整 Schema、全量回归、
全面能力资格、性能优化或完备证明材料放在首次体验之前。

方向探针和可用 Alpha 都必须各自记录 `CONTINUE`、`REDIRECT` 或 `REJECT`。探针 `CONTINUE` 只允许进入 Alpha；只有 Alpha 的
`CONTINUE` 才能进入工程夯实。方向错误时立即停止扩张，不能因为已投入代码或机械测试已经通过而继续堆叠实现。若最小真实探针本身
无法较快形成，应把它视为优先暴露的架构风险，而不是先开发更多内部组件。

输入持有、技术质量裁决和产品方向决定必须分离。用户可以持有现场问题并决定继续、改向、停止或最终接受，但正确性、完整性、引用支持、
边界判断和是否存在特判必须先由独立评测方裁决，不能把代码事实审核转嫁给用户，也不能用用户喜欢某种表达替代技术质量 PASS。

## 每个 Slice 必须包含

- 目标结果、触发和明确非目标；
- 当前行为与期望行为；
- 引用的 System Contract/Invariant，而不是复制正文；
- 受影响入口、Owner、数据迁移与兼容边界；
- 需要在编码前确定的跨模块接口语义；
- 关键风险、开放问题和失败关闭方式；
- 可执行的验收场景和 Finding 回写入口。
- 最小方向体验的真实入口、代表性任务、明确不做项、可见限制和体验后方向决策点。

## 不应预写

- 私有类、函数、表字段和内部状态枚举；
- 可由重构和测试低成本决定的算法步骤；
- 逐错误码、逐日志字段或逐 Mock 行为；
- 没有当前消费者的未来扩展点；
- 与 Contract 重复的大段背景和不变量。

## 何时先设计再编码

跨 Owner 权限、公开协议、不可逆数据、并发一致性、安全隔离或迁移语义必须先闭合设计。局部实现、可逆重构和算法选择可以通过最小代码/测试实验决定；若实验发现系统影响，立即进入 Finding 回写流程。

## Variance

实现与 Slice 不同不自动是错误。记录原因和证据：局部差异可直接修订 Slice；影响 System 的差异必须先暂停并升级；被延后的价值进入 Roadmap Candidate，不能埋在 Result 尾部。
