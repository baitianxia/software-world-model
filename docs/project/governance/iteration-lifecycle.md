# 迭代选择与生命周期

> 2026-10-14 重写（ITER-010-PDR-015）：由“按架构文档拆分任务”改为“按价值假设与实验推进，架构随证据细化”。旧版全文见 Git 历史
> （`codex/development` 的 `dfdcf6d` 及之前）。

## 1. 原则

1. **假设先于细化。** 产品目标（`SYS-PRODUCT-SUCCESS`）之下，最大的不确定是“世界模型能否让同一 Agent 答得更好”。凡是结论未被证据
   支持的设计，先用最小实验验证，再写成契约或架构；架构只承载已确认的边界与不变量。
2. **任务来自价值，不来自组件。** 每个任务对应一个用户可观察结果或一个待证伪的假设，而不是“把某个组件做完整”。
3. **时间盒优先于完整性。** 每个任务有日历截止日期；到期交付当时可运行的版本和证据，由用户决定下一步。
4. **失败是证据，不是新流程。** 普通失败留在当前任务内处理；不为单次失败新建计划修订、Result 或授权请求。
5. **检查点必须有架构评审。** 每个交付检查点都按 `PROJECT-GOVERNANCE-ARCHITECTURE-CHANGE` 的适配性清单评判架构是否仍支撑目标。

## 2. 一轮迭代的输入（一页 Proposal）

Proposal 只需回答六个问题，篇幅以一页为宜：

| 问题 | 要求 |
|---|---|
| 价值假设 | 本轮要证明或证伪的一句话假设，例如“同一 Agent 加入 L0—L2 认知后，在异质问题上比只读源码更正确或更完整” |
| 最早实验 | 能最快给出证据的最小实验或纵切，以及用到的问题集、对照组和判定规则 |
| 用户可见结果 | 本轮结束时用户在浏览器或命令行上新增能看到的能力 |
| 时间盒 | 每个任务的截止日期和整轮截止日期 |
| 退出条件 | 成功、失败和“证据不足”各自对应的下一步（继续、返工、转向、停止） |
| 边界 | 明确不做什么；需要的数据与外部调用授权范围 |

问题集、对照组和判定规则在实验前冻结；评测问题至少一半不参与开发；事实由独立的源码证据判定，任何一方答案都不是裁判。

## 3. 生命周期

```text
一页 Proposal ──用户确认──▶ 任务 1（时间盒）──▶ 检查点
                                   ▲              │ 交付包 + 架构评审 + 对照结果
                                   │              ▼
                                   └── CONTINUE / REWORK ◀── 用户决定 ──▶ REDIRECT（新一轮） / STOP
检查点结论稳定后 ──▶ 结晶：把已被证据支持的接口写成契约，必要时走架构变更
```

- **确认即授权。** 用户确认 Proposal 后，在其边界内开发不再逐项申请；只有数据、外部接收方、预算、写入或生产等范围变化才需新授权。
- **检查点。** 每个任务截止或提前完成时触发，也可由停止规则提前触发（见 `PROJECT-GOVERNANCE-PLAN-EXECUTION`）。
- **用户决定。** `CONTINUE`（进入下一任务）、`REWORK`（同任务按新策略重做，必须写明换了什么）、`REDIRECT`（假设被证伪，开新一轮）、
  `STOP`。
- **结晶。** 只有检查点证据支持、且已有真实调用方的跨模块接口才写入 `docs/system/contracts/`；局部规则留在代码与测试。

## 4. 检查点交付包

每个检查点向用户交付以下内容，缺一项即视为检查点未完成：

1. 可运行版本：启动方式、本地地址、精确提交、已知限制；
2. 实验结果：冻结问题集上各组的逐题结果、重大错误、遗漏与引用核对，以及失败最早发生的责任层；
3. 投入统计：本阶段按目录的代码、文档、门禁与测试增量（偏航信号，不是门禁）；
4. 架构评审结论：`FIT / FIT_WITH_ACTIONS / MISFIT` 及理由（见架构变更规则）；
5. 下一步选项：至少两个，附各自的风险与预计时间。

## 5. 实验与产品代码

- 用于证伪假设的探索代码放在 `validation/` 或独立实验目录，可以不满足产品契约，但必须可复现并保留结果。
- 实验结论支持假设后，才把对应能力以最小实现进入产品代码；实验结论不支持时，删除或归档探索代码，不为其补写契约。
- 产品代码仍须遵守架构基线的权威与安全不变量（只读来源、正式知识单路径、生成与审核分离、密钥隔离）。

## 6. 最少文档

活动迭代只保留文档检查要求的最小集合：

| 文件 | 内容 |
|---|---|
| `README.md` | 迭代索引与状态 |
| `proposal.md` | 第 2 节的一页 Proposal |
| `readiness-review.md` | 用户确认记录（谁、何时、确认了哪版 Proposal） |
| `verification-matrix.md` | 冻结的问题集、对照组与判定规则 |
| `manifest.yaml` | 当前动作及其允许/禁止路径（供门禁使用） |
| `development-design/` | 当前执行计划（任务、日期、检查点） |
| `findings/` | 按 `PROJECT-GOVERNANCE-IMPLEMENTATION-FEEDBACK` 门槛登记的发现 |

`project/current.md` 只指向活动迭代、活动任务和截止日期，不复制计划或状态机。

## 7. 完成定义

一轮迭代在以下条件全部满足时完成：

- 本轮价值假设得到明确结论（支持、证伪或证据不足），且结论附冻结问题集上的可复核证据；
- 最后一个检查点交付包完整，用户给出 `CONTINUE`（进入下一轮）、`REDIRECT` 或 `STOP`；
- 没有 `open` 状态的 Finding；被证据支持的接口已结晶为契约，架构变更已按规则完成；
- 失败与限制如实保留，不因后续成功删除。

代码完成、测试数量、文档数量或门禁通过本身都不是完成依据。生产启用不属于迭代完成的一部分，需要单独决定。

## 8. 与产品价值门的关系

产品价值按 `SYS-PRODUCT-SUCCESS` 第 5 条分层判定：先过归因门（同一 Agent 下世界模型 + 源码优于只读源码），再过强基线门（对比 current
Codex）。在归因门通过前，不进入跨工程、全量回归、性能或正式验收等夯实工作。
